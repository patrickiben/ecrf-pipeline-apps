Evaluation case study · synthetic data only

How the coding and de-identification assists were evaluated

Two of the four apps, the Coding QC assist and the De-identification review assist, have a second, optional "real model path" built from open-source models (Cactus Needle3, hnswlib, Laya and XGBoost). This page reports what that path and the default rule-based stand-in did on a labeled synthetic test set: how the data were built and split, how the probabilities were calibrated, what was measured, and where it failed.

Evidence label: Tools built (synthetic data only). The apps, the synthetic data generator and the evaluation scripts are working artifacts in this repository. Nothing here was run on real patient data, a licensed MedDRA release or real site notes, and nothing here is a validated system. The real-path build and measurement (2026-10-21 and 2026-10-22) were done in AI-assisted coding sessions (Claude Code), whose commits are authored "Claude" in the git history; every number on this page is read from a committed result file written by a script in eval/, not from a session's text.

The failures, stated plainly

  • Identifiers left readable. On 220 held-out synthetic notes holding 308 identifiers that should have been redacted, the real model path left 91 of 308 readable (80 direct identifiers, 11 indirect) and the stand-in left 108 of 308 (all direct). The leaks are formats neither proposer covers: 8-digit MRNs ("MRN: 21428912", 22 leaked), 7-digit phone numbers ("555-0185", 22), dates of birth written M/D/YYYY ("9/13/1940", 19) and names with no title in front of them (17). None of Needle3's 5 MRN proposals was right. This alone rules out using either path as a de-identification method without a person reviewing every record.
  • False redactions. The real path made 11 false positives the stand-in did not: drug names taken as patient names ("Alanine" twice, "Levothyroxine"), doses taken as phone numbers ("20 mg prescribed", "100 mg"), bare years taken as dates of birth, an MRN typed as initials, and 3 boundary slips on initials.
  • Colloquial verbatims are not solved. For phrasing such as "calcium down on bloods", the right preferred term ranked first for 52% on the real path against 46% for the stand-in, and none cleared the auto-code gate. The misses are mostly direction words: "calcium down" retrieves "Blood calcium increased" above "decreased", because Needle3's embedding does not separate them.
  • A weak probability that calibration made worse. Laya's "does this field hold a direct identifier?" answer had an AUROC of 0.69 and was biased low (fields that do hold one got a mean probability of 0.24). Fitting a temperature raised its expected calibration error from 0.445 to 0.485, because a temperature cannot fix a bias and the fitted value is shared with the other PHI question.
  • The worked examples did not reproduce the original deck. The illustrative scores the first version of the walkthrough showed (0.958, 0.971, 0.934, 0.882, and "three auto-code, one flags") were not reproduced: on the real path all four worked verbatims got the right preferred term at rank 1 but scored 0.04 to 0.12, so all four went to a human coder. See the case study.
  • Slow on a CPU. About 0.4 s per verbatim and 0.9 to 1.6 s per note, one record at a time, on a 4-vCPU cloud CPU. The real path is a batch job, not the sub-50 ms interactive tool the first deck targeted.
  • The re-ranker lowered top-3. It raised top-1 over plain retrieval order (0.747 to 0.778) but lowered top-3 (0.885 to 0.854), because several lowest-level terms under one preferred term crowd the right one out of the three exported candidates.

What was measured, on what data

All evaluation data come from eval/make_data.py (seed 42; rerunning it reproduces eval/data/ byte for byte). Everything is invented: terms carry 99-prefixed placeholder codes, not MedDRA codes, and the groupings are not MedDRA's hierarchy.

FileWhat it holds
dictionary.csv3,371 lowest-level terms under 519 preferred terms, in the shape of the demo dictionary: body-site pain, stiffness and swelling; fractures, wounds and burns; lab values increased, decreased and abnormal; infections by organ; common symptoms.
coding_eval.csv1,920 adverse-event verbatims, four per term: exact (a term typed lower-case), colloquial ("forearm feels weak"), misspelled ("palpitaitns") and negated ("denies nausea"). A negated verbatim has no correct code, so any auto-code of one counts as an error.
phi_fields.csv, phi_spans.csv880 free-text eCRF notes from 40 templates with 1,166 gold spans: 1,078 redaction targets (patient names, phone numbers, emails, MRNs, dates of birth, ZIP codes, initials, ages) and 88 identifier-shaped spans that are not targets on their own (a lone initial or ZIP code). The notes also carry look-alikes that are not identifiers: drug names, lab values, doses, times, kit and lot numbers.

How the shipped code was measured. eval/run_eval.py loads each app's own tier functions from its file (everything above its UI marker, through eval/_app.py), so the evaluation runs the code the apps ship rather than a copy. It runs the stand-in on the test split; builds the real Tier 2 and Tier 3 features on every split; fits the Laya temperatures on the calibration split; trains the XGBoost gate on the training split; writes those artifacts into a models dir; then reloads the app from that models dir and runs its real path on the test split. Those reloaded runs are the "real" numbers, and the script asserts that the reloaded app's calibrated probabilities match the ones the gate was trained on (to 0.002).

Scoring rules. Coding: top-1 and top-3 are measured on the 288 verbatims that have a correct code; the auto-code rate is over all 384; an auto-code is an error if its preferred term is wrong or the verbatim is negated. De-identification: a redaction counts as correct only on a strict match (same note, same start and end offset, same entity type); "left readable" counts gold targets with no overlapping redaction of any type, which forgives boundary and type slips and is the number that matters for privacy.

Grouped splits

A random row split would let the test set share terms and note templates with training, so a model could score well by memorizing them. Calibration

Laya answers each yes/no question with a probability: the softmax of its logits divided by a temperature. The checkpoint ships a temperature of 1.98; the script fits a new one on the calibration split with Laya's own fitting function and reports the test split before (shipped) and after (fitted). Expected calibration error (ECE) uses 10 equal-width bins; lower is better. A temperature changes how confident the probabilities are, not their order, so AUROC does not change.

Laya fits a temperature per answer type and option count only from 2,000 labeled records or more. The calibration splits here are smaller, so it fits one type-level temperature, and the two PHI questions share it. The indirect question's near-perfect AUROC reflects templated synthetic notes, an easy case, not a general result. The coding question's AUROC of 0.74 means Laya separates negated from plain verbatims only moderately; it is the re-ranker, combining that answer with the retrieval features, that kept every negated verbatim below the gate.

  • The gain is mostly on misspellings (top-1 0.81 against 0.19), and the re-ranker auto-coded about half of them with no error. Exact matches were all auto-coded.
  • The gate value did not matter on the real path here. The re-ranker's scores were bimodal (134 above 0.95, most of the rest below 0.5, none between 0.88 and 0.90). On the stand-in, the same 0.02 moved 6 negated verbatims across the gate.
  • Case mattered. Needle3's embedding is case-sensitive ("insomnia" scored 0.948 against "Insomnia", below several unrelated terms). The first real run had this defect; the app now embeds lower-cased text on both sides, which is worth 0.125 top-1 on retrieval alone.
  • Small dictionary. 3,371 terms is far sparser than a full release (about 86,800 lowest-level terms). Accuracy at release scale was not measured and should be expected to be lower.

P = precision, R = recall, strict match on offsets and entity type.

  • The real path finds more names. Needle3 proposes names with no title in front ("Spoke with Linda Miller"), which the stand-in's patterns require, and the gate keeps most of them: name recall 0.33 to 0.74 at 0.94 precision.
  • It lost some indirect attributes the stand-in kept (age recall 1.00 to 0.73, initials 1.00 to 0.89): the stand-in redacts any indirect attribute when two co-occur, and the trained gate learned a softer rule.
  • The gate leans on span evidence, not on Laya. With direct_pii weak and biased low, the redactions that are right are right because of the span features.

Retrieval index (coding Tier 2): Needle3 vectors are 3072-dimensional. Over the 3,371-term dictionary the index held 40.4 MB, search took 0.54 ms (median) against 0.60 ms for exact brute force, and recall@10 against exact search was 0.994. At a full release's size, measured on 86,800 random unit vectors of the same width (index cost only, not retrieval quality), the index held about 1,040 MB and search took 5.8 ms. Embedding the verbatim (about 30 ms) costs more than the search.

Before the build: feasibility checks

Before any build work (Stage 0, 2026-10-21 and 2026-10-22), both models were downloaded, loaded offline on a CPU and checked against what the apps assumed. The full record is in FEASIBILITY.md. What it changed:

  • The assumed embedding was wrong. The original design said "384-dim (SapBERT)"; Needle3's vectors are 3072-dimensional and it is not a biomedical encoder. Its similarity scores are compressed (unrelated terms scored 0.93 against 0.96 for the right one), so no fixed cosine cutoff carries over.
  • Laya is over-confident as shipped (its authors say so) and near chance zero-shot on its authors' decision benchmark. One measured example went the wrong way: "Does the patient report a headache?" on "Patient denies headache." gave 0.655. That is why calibration and a labeled negation set were required before any Laya output drove a decision.
  • Five wiring defects in the apps would have stopped or mislabeled the real path: the model modules were never bound to names; the Laya call used route(), which returns a routing decision, not answers; the banners claimed REAL when only a library was importable; the guarded artifact names (needle3.onnx, laya.onnx) do not exist in either model repository; and the Laya probe reported REAL with torch absent. All five were fixed, and each fix is pinned by an always-run check in tests/qc_test.py (RW1 to RW16, stub packages, no models needed).
  • Network and telemetry. Needle3's Python package sends usage telemetry unless it is switched off, and its loader asks the Hugging Face Hub for a config file on every load, even with the weights cached. The apps set NEEDLE_TELEMETRY=0, DO_NOT_TRACK=1 and HF_HUB_OFFLINE=1 before any model loads and read only the models dir. An unrelated PyPI package also installs the import name needle; the apps reject it.

What this does not show

  • Real data. Accuracy on a licensed MedDRA release or on real site notes is unknown and should be expected to be lower.
  • Retrieval quality at release scale. The 86,800-term figures are index cost on random vectors.
  • Participant risk screening and Central statistical monitoring. Neither has a trained-model path or a labeled evaluation; they run labeled rule-based stand-ins (plus optional scikit-learn and POT detectors in the monitoring app), checked against injected synthetic signals in the QC suite.
  • Validation. These are evaluated prototypes, not validated systems. Reported study numbers belong to the sponsor's validated, double-programmed SAS or R programs; nothing here replaces that or the medical coder's and privacy reviewer's judgment.
